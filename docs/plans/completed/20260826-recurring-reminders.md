# Повторювані нагадування (recurring reminders)

## Overview

Замінити iOS Reminders для справ із повторенням: «виставити кешбек 1-го числа о 8:00»,
«записати пробіг авто», «полити кактус раз на 2 тижні».

Пункт уже стояв у беклозі `ARCHITECTURE.md:477` («Reminders. Записати щось, передати
щось… they get their own table»). Окремого GitHub issue не існує.

Як інтегрується:
- **Home Assistant** тягне ICS-фід і зранку каже, що сьогодні заплановано. Ранкового
  пушу від бота немає — це була б дубль-нотифікація.
- **Бот** пише лише про незакрите: один вечірній дайджест із інлайн-кнопками.
- **Mini App** — основна точка входу: створення правил і відмітки «зроблено».
- **Web UI не чіпаємо.**

## Solution Overview

**Межа проходить рівно по `now`, по МОМЕНТУ, а не по даті.**

- **`due_at <= now` — матеріалізовані рядки.** Рядок створюється тоді, коли входження
  настало. Це заморожений факт: «було належно в цей момент за цією версією правила».
  Правка правила заднім числом його не чіпає.
- **`due_at > now` — рахується з версіонованих правил.** Горизонт нескінченний,
  фонової задачі продовження немає, правка правила видна одразу.

Різати по **даті** не можна: о 08:00 нагадування на сьогодні 20:00 ще не має рядка,
і при поділі «минуле й сьогодні з рядків» воно зникло б і з календаря, і зі списку.

`pending`-рядок у минулому є **доказом**, що входження справді настало і його прогавили,
а не результатом перерахунку за сьогоднішнім правилом.

**Правило версіоноване.** Замість змінюваного рядка — список версій із `valid_from_at`.
Розгортаючи вікно, ріжемо його по версіях і кожен відрізок розгортаємо своєю.

**Повний RRULE, не закритий набір режимів** — до `family-hub` планується перенос
`home-meters`, де потрібен останній день місяця; заняття згодом можливо перероблять
на той самий примітив.

**Розгортаємо в Go, в ICS шлемо звичайні VEVENT.** Розгортання в Go все одно потрібне
для Mini App і для пінка — отже це один шлях коду. Сирий `RRULE` у фіді дав би другий,
незалежний шлях (HA розгортає сам), і два шляхи можуть розійтися.

### Ключове рішення: `DTSTART` замість власних колонок

У RFC 5545 `DTSTART` несе і точку відліку, і час доби. Тому окремі `time_of_day`,
`anchor_date`, `freq`, `interval`, `byday`, `bymonthday` схлопуються у два поля.

### Ідентичність входження — `due_at`, не дата

Повний RRULE допускає кілька входжень на добу (`BYHOUR=8,20`, `FREQ=HOURLY`).
Ключ `UNIQUE(reminder_id, due_date)` схлопнув би їх в один рядок, тож ключуємо по
`due_at` (локальний datetime до хвилини). UID у фіді — теж по `due_at`.

### Матеріалізація — власний тікер, не `RunDigests`

`RunDigests` рано виходить без `NotificationsEnabled` або без notify-чату
(`digests.go:15-28`), а дайджести навмисно необов'язкові (`bot.go:39`). Повісити на
нього матеріалізацію означало б поставити **цілісність даних за прапорець
необов'язкових сповіщень**: вимкнув дайджести — перестала писатись історія.

Тому матеріалізація — окремий тікер рівня застосунку, запускається з `main.go`
незалежно від бота, плюс **один прохід на старті**.

Тікер самозцілювальний: кожен тік розгортає правила за останні **30 днів** і вставляє
рядки для входжень без рядка. `UNIQUE(reminder_id, due_at)` робить це ідемпотентним,
тож простій до 30 днів наздоганяється сам, без watermark-стану.

Нижня межа наздоганяння — `max(now-30d, active_since)`: інакше ввімкнена після паузи
справа насочиняла б `pending` за весь час, коли була вимкнена.

### Політика DST

`due_at` — стінний локальний час. Це дає правильну поведінку на обох переходах без
жодної валідації:

- **Осіннє повернення** (локальний час буває двічі): бібліотека віддає **одне**
  входження, на другому (післяперехідному) інстанті. Схлопувати нічого не треба —
  нагадування одне, а не два. Перевірено тестом, а не взято з документації.
- **Весняний провал** (локального часу не існує): нормалізується вперед, 03:30 стає
  04:30 того дня. Входження не зникає і не помиляється.

Обидва випадки закріплені тестами в `internal/recur/recur_test.go`.

Подвійного спрацювання пінка теж немає: `lastNag` дедуплікує по даті.

### Що лишилося компромісом

- **Аменд минулої версії правила** (випадок «я помилився, там завжди було 5-те») не
  перебудовує вже матеріалізовані рядки — вони заморожені за визначенням. Форма має
  два сенси: «з такого-то числа робимо інакше» (нова версія, дефолт) і «виправити
  запис» (аменд). Другий лишає розбіжність, вирішується вручну.
- **Простій довший за 30 днів** залишить ті входження без рядків назавжди.
- **Відмітити майбутнє входження не можна.** `Mark` відхиляє `due_at > now`: рядок
  у майбутньому був би невидимий для фіду (той рахує майбутнє з правил) і осиротів би
  після правки правила. Хочеш закрити наперед — закриєш, коли настане.

## Technical Details

### Схема (`internal/db/migrations/0004_reminders.sql`)

```sql
CREATE TABLE reminders (                    -- що це за справа
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  person TEXT NOT NULL DEFAULT '',
  duration_min INTEGER NOT NULL DEFAULT 15,
  active INTEGER NOT NULL DEFAULT 1,
  active_since TEXT NOT NULL,               -- коли ввімкнено востаннє; підлога бекфілу
  note TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  deleted_at TEXT NOT NULL DEFAULT ''
);

CREATE TABLE reminder_rules (               -- як воно повторювалось, з якої миті
  id INTEGER PRIMARY KEY,
  reminder_id INTEGER NOT NULL REFERENCES reminders(id),
  valid_from_at TEXT NOT NULL,              -- '2026-09-15T00:00', включно
  dtstart TEXT NOT NULL,                    -- '2026-08-01T08:00' відлік + час доби
  rrule  TEXT NOT NULL,                     -- 'FREQ=MONTHLY;BYMONTHDAY=1'
  created_at TEXT NOT NULL,
  UNIQUE(reminder_id, valid_from_at)
);

CREATE TABLE reminder_occurrences (         -- що справді настало
  id INTEGER PRIMARY KEY,
  reminder_id INTEGER NOT NULL REFERENCES reminders(id),
  rule_id INTEGER NOT NULL REFERENCES reminder_rules(id),   -- яка версія породила
  due_at TEXT NOT NULL,                     -- '2026-09-01T08:00', локальний стінний
  status TEXT NOT NULL,                     -- pending | done | skipped
  done_at TEXT NOT NULL DEFAULT '',
  done_by TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  UNIQUE(reminder_id, due_at)
);

CREATE INDEX idx_reminder_occ_due ON reminder_occurrences(due_at, status);
CREATE INDEX idx_reminder_rules_lookup ON reminder_rules(reminder_id, valid_from_at);
```

`valid_from_at` — datetime, а не дата: інакше нова версія «з сьогодні», створена о
10:00, конфліктувала б із сьогоднішнім входженням на 08:00, яке вже відпрацювало.

`rule_id` робить рядок самоописовим: видно, яка версія правила його породила.

`UNIQUE(reminder_id, due_at)` — ті самі ліки, що issue #10 для візитів: гасить гонку
між чекбоксом Mini App, кнопкою бота і тікером матеріалізації.

`person` — просто рядок, як `appointments.person`. **Без маршрутизації сповіщень по
людях** — у персон немає ані identity, ані CRUD (відкритий issue #41).

### Статуси входження

| Статус | Значення | Вечірній пінок |
|---|---|---|
| `pending` | настало, ніхто не закрив | **пінає**; у минулому = забули |
| `done` | зробив | не пінає |
| `skipped` | свідомо пропустив | не пінає |

Нічого не виводиться — усі три стани є рядками.

### ICS

Вікно −30…+90 днів, що **розрізається рівно по `now`**: `due_at <= now` беруться з
`reminder_occurrences` (реальні рядки зі статусом), `due_at > now` розгортаються з
версій правил.

```
BEGIN:VEVENT
UID:reminder-3-20260901T0800@familyhub
DTSTAMP:...
DTSTART:20260901T050000Z          ← 08:00 Kyiv
DTEND:20260901T051500Z            ← + duration_min
SUMMARY:Кешбек · Олег
END:VEVENT
```

Закриті (`done`/`skipped`) **залишаються** у фіді з префіксом `✓` у SUMMARY.

**Суфікс UID `@lessons` → `@familyhub` для всіх джерел.** Рішення власника; лишався
від `family-visits`, користувачу не видний.

Наявний коментар в `ics.go` стверджує, що HA видалить і перестворить усі події. Це
**не підтверджено**: `remote_calendar` — read-only інтеграція, що качає фід і будує
таймлайн, а не сховище записів по uid. Коментар замінюється на чесний.

Реальний ризик — не HA, а **клієнти, що зберігають події по UID** (Apple Calendar):
там перейменування = зникли старі, з'явились нові. Перевірка перед деплоєм — у
Post-Completion.

### Бот

Новий env `REMINDER_NAG_TIME` (напр. `20:00`). Третій тригер у `RunDigests` поряд із
`lastDaily`/`lastWeekly` — додається `lastNag`. Тікер уже щохвилини.

**Матеріалізація тут НЕ живе** — вона окремий тікер із `main.go` (див. вище).

```
Сьогодні не закрито:

• Кешбек · Олег   (було 8:00)
• Пробіг авто     (було 9:00)

[✓ Кешбек] [✓ Пробіг] [✗ пропустити]
```

**Команд бота не додаємо** — керування через Mini App і кнопки, це явна вимога.

### Mini App

```
GET    /mini/api/reminders                  список справ + найближчі входження
POST   /mini/api/reminders                  створити (справа + перша версія правила)
PUT    /mini/api/reminders/{id}             змінити назву/особу/тривалість/активність
POST   /mini/api/reminders/{id}/rules       нова версія правила (з valid_from_at)
PUT    /mini/api/reminders/{id}/rules/{rid} аменд наявної версії (виправлення запису)
DELETE /mini/api/reminders/{id}             м'яко видалити
POST   /mini/api/reminders/{id}/occurrences відмітити входження (due_at + status)
POST   /mini/api/reminders/preview          валідувати rrule, віддати найближчі 5 дат
```

Форма правила: чипси під часті випадки — щодня, раз на 2 тижні, щомісяця, останній
день місяця, через день — кожен пише готовий RRULE-рядок; плюс поле сирої RRULE.
При зміні правила форма питає **«з якого моменту»**, дефолт — від зараз (нова версія);
альтернатива «виправити запис» амендить поточну версію.

  UID, покажуть зникнення старих і появу нових
